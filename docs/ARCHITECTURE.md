# 架构与关键决策

## 为什么不让大模型直接决定资格

申报条件通常包含日期、金额、比率、称号和互斥关系。如果仅通过提示词让模型判断，容易出现计算误差、遗漏否决条件、把“条件符合”误写成“现在可以提交”等问题。因此系统拆成四层：

1. 文档层：保留原文件、下载来源和 SHA-256；
2. 检索层：从 PDF/DOCX 切片，使用中文字符及二元组 BM25 检索；
3. 决策层：结构化规则、材料检查和一致性计算；
4. 生成层：只根据已验证事实生成报告和初稿，未知信息显示为占位符。

## 状态分离

每个政策输出两个独立状态：

- `window_status`：open、upcoming、closed、unknown；
- `eligibility_status`：eligible、not_eligible、needs_information。

例如，虚构企业华芯精密的“小巨人”硬条件可以全部满足，但在 2026-08-10 评估时窗口已关闭。系统不会把两者混成“可申报”。

## 可追溯性

每条规则包含：

- 企业事实字段；
- 比较操作符和阈值；
- 通过/失败/未知状态；
- 官方文件名称、链接、页码或条款；
- 本次执行的事件轨迹。

政策 JSON 是人工复核后的决策基线。正则抽取结果只作为候选，不会自动升级成正式规则，避免错误抽取直接影响资格判断。

## 人工审批

`assess` 生成内部草稿并将运行状态设为 `pending`。只有 approver 或 admin 角色能批准；只有批准后才能执行导出。项目故意不提供连接真实政府平台的提交工具。

## 生产化差距

- 将演示用 `X-Role` 替换为 SSO/OIDC 和服务端授权；
- 将本地 JSON 审计替换为追加写、不可篡改的审计存储；
- 为政策版本建立生效、废止和地方细则继承模型；
- 对上传文件执行恶意文件、涉密、个人信息和商业秘密检测；
- 大模型输出必须通过事实引用、规则回算和人工复核；
- 增加多租户隔离、密钥管理、加密、备份及数据保留策略。
